# Параллельная работа трёх команд и недельный релиз

## Распределение команд

| Команда | Ветка | Ответственность | Пример результата |
|---|---|---|---|
| Платежный модуль | `feature/payments` | Создание платежа, прием callback от платежного провайдера, проверка статуса, защита от повторной обработки уведомления | Платеж создаётся один раз, статус корректно обновляется |
| Складской учет | `feature/inventory` | Получение остатков, резервирование товара под заказ, снятие резерва при отмене | Остатки синхронизируются и не становятся отрицательными |
| Каталог | `feature/catalog` | Импорт карточек товара, проверка обязательных полей, сопоставление идентификаторов | Новые товары импортируются без дублирования |

## Пошаговый сценарий недели

### Понедельник — начало параллельной разработки

Ведущий разработчик проверяет, что `develop` содержит последние объединённые изменения. Каждая команда получает свою копию репозитория, обновляет `develop` и создаёт собственную feature-ветку. Команды не коммитят напрямую в общую ветку.

- Платёжная команда работает в `feature/payments`.
- Складская команда работает в `feature/inventory`.
- Команда каталога работает в `feature/catalog`.

Все три ветки создаются от одной актуальной точки `develop`, после чего разработка идёт параллельно.

### Вторник–среда — коммиты и Pull Request

Каждая команда делает небольшие коммиты, отправляет свою ветку на GitHub и открывает Pull Request в `develop`. В описании PR указывается задача, список изменений и результат тестирования.

Слияния в `develop` выполняются после проверки кода и успешного CI. Сам процесс разработки параллельный, но слияния в общую ветку проходят последовательно, чтобы команда могла проверить актуальное состояние `develop` после каждого PR. Если два разработчика изменили один общий файл, конфликт разрешается до слияния.

После каждого слияния запускаются тесты. После объединения всех трёх модулей запускается полный набор интеграционных тестов: каталог передаёт данные о товаре, склад обновляет остаток, платежный модуль получает заказ на оплату.

### Четверг — создание релизной ветки

Когда функции текущей недели согласованы, ответственный создаёт `release/v1.12.0` от `develop`. Это означает заморозку функций для версии 1.12.0: новые возможности в релизную ветку не добавляют. Допускаются только исправления найденных ошибок, обновление документации и подготовка версии.

Пока тестировщик стабилизирует `release/v1.12.0`, разработчики могут начинать следующий цикл в новых feature-ветках, созданных уже от `develop`.

### Пятница — выпуск

Тестировщик проверяет критические пользовательские сценарии: импорт товара, обновление остатков, резервирование, создание платежа и обработку ответа платежного провайдера. Дополнительно выполняются регрессионные тесты и проверки AppSec.

После успешной проверки `release/v1.12.0` сливается в `main`. Коммит релиза помечается тегом `v1.12.0`, после чего именно эта версия разворачивается в production. Затем релизная ветка сливается обратно в `develop`, чтобы исправления стабилизации не потерялись.

На следующей неделе цикл повторяется, например с веткой `release/v1.13.0`. Таким образом, `release/v1.x` — не одна постоянно используемая ветка, а шаблон для конкретного номера каждой недельной версии.

## Как три feature-ветки объединяются

1. `feature/payments` проходит PR и сливается в `develop`.
2. `feature/inventory` проходит PR и сливается в обновлённую `develop`.
3. `feature/catalog` проходит PR и сливается в обновлённую `develop`.
4. Запускаются общие интеграционные тесты всех трёх модулей.
5. Из проверенной `develop` создаётся `release/v1.12.0`.

При этом порядок слияния трёх PR может быть другим. Главное — чтобы все ветки были проверены, а интеграционные тесты запускались уже на общей версии `develop`.
