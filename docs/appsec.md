# AppSec: место SAST в жизненном цикле

SAST (Static Application Security Testing) — статический анализ исходного кода без запуска приложения. Он помогает находить потенциально опасные конструкции: небезопасную обработку входных данных, ошибки проверки доступа, возможные утечки секретов и другие проблемы.

Для интеграционного шлюза проверки нужно запускать не в одной точке, а на нескольких этапах:

1. **Во время локальной работы в `feature/*`.** Разработчик может запускать анализатор до отправки изменений. Это позволяет исправлять проблемы сразу, пока изменён небольшой участок кода.
2. **Обязательно при Pull Request из `feature/*` в `develop`.** CI запускает SAST, модульные тесты, secret scanning и проверку сторонних библиотек (SCA). Слияние блокируется при критических уязвимостях или неуспешных обязательных проверках.
3. **Повторно на `develop` и особенно в `release/*`.** После объединения трёх модулей проверяется уже общий код. На релизном этапе выполняется полный набор тестов и проверок зависимостей, потому что ошибка может появиться из-за взаимодействия компонентов.
4. **Обязательно для `hotfix/*`.** Даже при срочном исправлении анализ безопасности и регрессионные тесты пропускать нельзя. Проверка должна быть ускоренной, но не отменённой.
5. **Перед публикацией в `main`.** Проверяется именно тот коммит/артефакт, который будет выпущен и помечен тегом.

SAST лучше подключить как автоматическую проверку в CI для Pull Request. Тогда результат виден команде до слияния. Ранний анализ снижает цену исправления ошибки, а повторная проверка релиза помогает обнаружить проблемы, появившиеся после интеграции. Дополнительно применяются SCA для библиотек, secret scanning для токенов и паролей и динамические проверки на тестовом стенде.
