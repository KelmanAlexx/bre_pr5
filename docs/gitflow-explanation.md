# Назначение веток Git Flow

Git Flow разделяет разработку, интеграцию, подготовку релиза и сопровождение уже опубликованной версии. Это помогает нескольким группам работать параллельно и не помещать незаконченный код в стабильную версию.

## `main` — стабильная ветка

- Содержит только проверенные версии, которые готовы к эксплуатации (production).
- Прямые коммиты разработчиков запрещены: изменения приходят через слияние `release/*` или `hotfix/*`.
- После каждого выпуска коммит релиза получает тег версии, например `v1.12.0`. Срочное исправление получает следующий patch-тег, например `v1.12.1`.
- Из `main` создают `hotfix/*`, потому что исправлять нужно именно опубликованную версию.

## `develop` — интеграционная ветка

- Является общей базой для разработки следующей версии.
- От неё создают все `feature/*`.
- В неё сливают готовые функции после Pull Request, проверки кода и автоматических тестов.
- На ней проверяют совместную работу платежей, склада и каталога.
- От неё создают `release/*`, когда набор функций для очередного выпуска зафиксирован.

## `feature/*` — ветки отдельных функций

- Каждая ветка создаётся от актуальной `develop` и решает одну задачу или группу тесно связанных задач.
- В данном проекте три команды одновременно используют `feature/payments`, `feature/inventory` и `feature/catalog`.
- Разработчики делают коммиты и отправляют ветки на сервер независимо друг от друга.
- После проверки Pull Request ветка сливается в `develop`, обычно с `--no-ff`, чтобы в истории был виден отдельный этап разработки функции.
- После успешного слияния feature-ветку удаляют.

## `release/*` — подготовка конкретного релиза

- Создаётся от `develop`, когда функции текущего цикла готовы и новые изменения временно запрещены (feature freeze).
- В неё вносят исправления ошибок, обновляют номер версии, документацию и настройки выпуска.
- Проводят регрессионное, интеграционное и безопасностное тестирование.
- После успешной проверки сливают в `main` и ставят тег версии, а затем сливают обратно в `develop`, чтобы исправления релиза сохранились в будущей разработке.
- Имя `release/v1.x` — шаблон. Для каждой недели нужна отдельная конкретная ветка, например `release/v1.12.0`, затем `release/v1.13.0`.

## `hotfix/*` — срочное исправление production

- Создаётся непосредственно от последнего стабильного коммита `main`, а не от `develop`.
- Используется только для критических проблем, которые нельзя ждать до следующего недельного релиза: например, уязвимость, повторное списание или полная остановка обмена с платежным шлюзом.
- Исправление проходит ускоренную, но обязательную проверку: тесты, code review, SAST и проверку зависимостей.
- После этого hotfix сливается в `main` и получает patch-тег, например `v1.12.1`.
- То же исправление переносится в `develop`, а если уже готовится релизная ветка — и в неё, чтобы проблема не вернулась.

## Общее правило движения изменений

`feature/*` → `develop` → `release/*` → `main`.

От `main` отдельно ответвляется `hotfix/*`, который после исправления возвращается в `main` и `develop` (и при необходимости в активную `release/*`).
